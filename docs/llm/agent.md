# Agent 与工作流

模型从"只会说"到"能做事"：先能调用工具，再把工具调用编排成流程，最后让模型自己规划步骤。

| 技术 | 解决什么问题 | 优势 | 劣势 |
|---|---|---|---|
| Tool Calling | 让模型调用函数，比如查数据库、调接口 | 模型从"只会说"变成"能做事" | 模型可能选错工具、传错参数，或者反复调用 |
| MCP | 工具接入的统一协议 | 一个工具写一次，多个 AI 应用都能接 | 多一层服务要部署和维护，权限要单独管 |
| Skill | 把操作流程和业务经验写成可复用的说明 | 经验沉淀下来，不用每次重新交代 | 依赖模型读懂并照做，复杂流程仍可能跑偏 |
| Workflow（LangGraph） | 把流程编排成有分支、有并行、有循环的图 | 每次走同一条路，结果稳定，出错能定位到节点 | 只能处理设计好的流程，遇到新类型的问题要改图 |
| Agent（Deep Agents） | 模型自己规划步骤、调工具、整理结果 | 能处理多步、开放式的任务 | 更慢更贵，结果不稳定，可能编造或"纠正"工具结果 |
| 子智能体 | 主智能体把子任务派给专门的智能体 | 每个子智能体上下文干净，分工清楚 | 主智能体汇总时可能改写子智能体的结果，要在提示词里约束 |

## 我的实践

**确定的流程用 Workflow，开放的问题用 Agent。** Text2SQL 的步骤是固定的，要求结果稳定、出错能定位，所以我用 LangGraph 工作流。"GMV 为什么下降"这类需要多步分析的问题，才值得交给 Agent。两者可以组合：把整个工作流包装成一个工具，交给 Agent 调用。

**LangGraph 并行节点会一起失败。** 同一个超步里任何一个节点报错，整个超步都失败。我遇到过 `recall_value` 缺依赖报错，结果和它并行的 `recall_column` 也一起失败，看起来像是 `recall_column` 有问题。

**Agent 会改写结果，要显式约束。** 在 Deep Agents 主/子智能体实验里，我给翻译、天气、计算三个子智能体写了固定的测试回答。主智能体汇总时自己"纠正"了计算结果，还编造了天气。在主智能体提示词里加上"原样转述、不准修改、不准编造"之后，三项结果都原样输出。

**Deep Agents 有开源版和托管版。** 开源版用 `create_deep_agent` 自己部署；托管版（Managed Deep Agents）运行在 LangSmith 上，要付平台费，目前只有美国区。公司内部的问数项目选开源版加 FastAPI 自己部署，只付大模型的费用。
