# 检索与 RAG

模型不知道你公司的库表和业务口径。RAG（检索增强生成）的做法是：先从自己的资料里检索出相关内容，再交给模型回答。

| 技术 | 解决什么问题 | 优势 | 劣势 |
|---|---|---|---|
| 向量库（Qdrant） | 存向量，做相似度检索 | 检索快，支持按 payload 过滤 | 数据重复写入很难察觉，需要确定性 ID 保证幂等 |
| 全文检索（ES + IK） | 关键词精确匹配 | 适合精确的取值，比如 WHERE 里的"华北" | 不懂同义词，"销售额"找不到"订单金额" |
| RAG | 先检索相关资料，再交给模型回答 | 模型不用知道全部知识，能用上私有数据 | 检索不准，后面全错；检索质量决定上限 |

## 我的实践

**字段用向量检索，取值用全文检索。** 我用本地 bge 模型实测了几组取值的相似度：

| 两个值 | 相似度 |
|---|---|
| 北京 / 南京 | 0.741 |
| 北京 / 天津 | 0.699 |
| Mate60 / Mate70 | 0.772 |

检索阈值是 0.6，这些都会被误召回。WHERE 条件里的值错一个字结果就错，所以取值必须走 ES 精确匹配。字段名则相反，需要"销售额能匹配到 `order_amount`"这种模糊能力，所以走向量。两者是分工协作，不是二选一。

**向量库要保证重复写入不产生重复数据。** 构建脚本最初用 `uuid4` 生成点 id，每次运行都是新 id，跑了 4 次后字段集合从 98 个点涨到 400 个点，检索结果里同一个字段重复出现。改成 `uuid5(命名空间, 字段id + 文本)` 后，同样的输入永远得到同样的 id，重跑就是覆盖，计数保持 98。

**检索不到的东西要程序补齐。** 表的主外键不会被语义检索召回，但没有它们大模型写不出 JOIN。所以在合并召回结果时，按表从元数据库补上主外键。
